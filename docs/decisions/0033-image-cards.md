# 0033. Image cards (Roadmap Task 8b): renderer, font, limit; Stage A built, Stage B waits

Source: the user, 2026-10-27. Requirement: a flashcard is sent in Slack as an image that we generate (a white card with the question text, no teacher upload); the options stay as numbered text under the image; the buttons stay the same. The user approved the plan with two answers: a 500-character limit for the question, rejected above it; no file-id storage, one upload per delivery (revisit after the spike with measured latency). Follows [0029](0029-task8-slack-wiring-choices.md) (#13: the options stay text, 2,900 REST cap), [0020](0020-slack-spike-choices.md), [0023](0023-local-first.md).

## Stages

- **Stage A (built):** `src/render/` (the renderer), the vendored font, `npm run render:samples`, `scripts/image-spike.ts` (user-run), `files:write` in the manifest, tests R1 to R8, docs. It changes nothing that runs in production: not `port.ts`, `web.ts`, `card.ts`, `fake.ts`, `scheduler.ts`, REST, MCP, `src/trace` or `docs/baseline/trace.json`.
- **Stage B (not started, waits for the user's go-ahead after the spike):** `SlackPort.postCard(to, message, image?)`; the upload and the image block in `web.ts`; `buildCardMessage` with an image; the scheduler renders in its shared `postCard` (tick, stale-claim re-send, 6b-2 reminders); the REST 500-character check with `question_too_long`, `unsupported_character` and `empty_question`; the MCP tool description; the trace recorder (`<image 1200x630>`, never bytes or a hash, because the hash may differ per platform); `FakeSlack` takes the image; the baseline diff (accepted only with `scenario:compare -- --accept` after the user OKs it).

## Choices

| # | choice | why |
| --- | --- | --- |
| 1 | Renderer: `@napi-rs/canvas` 1.0.13 (MIT), pinned exactly | one package with prebuilt binaries (29 MB darwin-arm64, 31 MB linux-arm64, 37 MB linux-x64); `measureText` makes shrink-to-fit a plain loop; 12 to 17 ms for a short card, about 80 ms for 10 lines. Rejected: satori 0.63.2 + resvg-js 2.6.2 (MPL-2.0, two packages, no measure API, so the fit needs a render-and-measure loop; its missing glyphs draw a visible box, which is nicer, but we refuse them earlier anyway) |
| 2 | Font: Inter (OFL 1.1), `Inter[opsz,wght].ttf` registered as family `RetainInter`, default weight | covers Latin with umlauts, Polish, Ukrainian and Russian Cyrillic, Greek and common maths and arrows; 877 KB. PT Sans lacks Greek, Noto Sans lacks the maths signs and is 2 MB. The canvas of satori cannot use variable fonts reliably, canvas can (checked by rendering) |
| 3 | Vendoring: `scripts/vendor-font.ts` downloads from `google/fonts` at commit `a4c0b21f839d7ac65a7d8b49eb81bddd110774a3` and refuses any file whose sha256 differs; both files are committed in `src/render/fonts/`. `Inter.ttf` sha256 `29160a80ff49ddcab2c97711247e08b1fab27a484a329ce8b813d820dc559031` (876,576 bytes), `OFL.txt` sha256 `5b9321a4298cfeb6b34354164a1c3afc3db114569984c502b9b35d988fd58c57`. `npm run font:vendor -- --check` verifies the committed files | no hand-copied binary, the licence text sits next to the font |
| 4 | Glyph rule: the cmap of the font is turned into `src/render/glyphs.ts` (205 ranges, `npm run font:glyphs`, fontkit 2.0.4 as a devDependency only); `validateQuestion` refuses any character outside it with `unsupported_character`. A test compares the committed ranges with the font | canvas falls back to SYSTEM fonts for missing glyphs (on the development Mac it drew emoji, Arabic and Chinese): the image would then differ per host, and on a bare server show tofu. Emoji, right-to-left scripts and CJK are therefore refused, not drawn |
| 5 | Card: 1200x630 white PNG, margins 80 px, text `#111111`, left aligned, block centred vertically, line height 1.3, font 64 px shrinking in 2 px steps to 28 px. Only the question is drawn (no card number, no course title) | Slack scales to the message width; 28 px is the readable minimum on a phone. The options stay text, so the question alone is the image |
| 6 | Limit: 500 characters of the sanitized question (code points, not UTF-16 units). Above it, or when the text does not fit at 28 px (for example 500 wide capitals), `question_too_long`. Nothing is truncated and there is no text-card fallback for long questions | the user's answer; a long question belongs in the options or in material |
| 7 | Sanitizing, in this order: line ends to `\n`; remove controls, soft hyphen, zero-width and directional characters, variation selectors, tags, BOM; Unicode spaces to a space; NFC; a combining mark needs a base and a base keeps at most 2; runs of spaces collapse; 3 or more newlines become 2; ends trimmed. The 500 limit counts what remains; the alt text and the Slack `text` must use the same sanitized text (`CardImage.text`) | no markup is interpreted (canvas draws plain text), nothing invisible can change the layout or the meaning, Zalgo cannot leave the margins |
| 7a | Review fixes: private-use code points are excluded from the glyph list (Inter's icon glyphs draw outside the margins); input over 5,000 characters is refused before sanitizing (a 10 MB string must stay cheap); the margin is 80 px because left bearings reach about 4 px, and the wrap width is 16 px narrower than the text box because ink can overhang the measured advance by about 12 px (stacked marks) | independent review of the diff |
| 8 | Same input gives the same bytes on one machine (tested). Cross-platform byte equality is NOT claimed, so no golden hash is committed. Tests assert decoded pixel properties instead (size, white background, ink only inside the margins, also for hostile input) | the engine and its binaries differ per platform |
| 9 | One upload per delivery, no file id stored, no migration. Revisit after the spike with the measured upload latency and whether one file id works for another user | the user's answer |
| 10 | The spike is a user-run script that duplicates the client options of `createSlack` and builds the upload and the image-block post itself; only `slackPort(...).lookupEmail` is the production adapter | Stage A must not edit production files |

## Spike run 1 (the user, 2026-10-27): the post was rejected

Reported by the user: `filesUploadV2` answered `ok=true` with a private file id; then `chat.postMessage` with the image block answered `invalid_blocks` ("invalid slack file", json pointer `/blocks/0/slack_file.id/slack_file`). Nothing was posted. Stage A stays unchanged in production; the spike script now runs a diagnosis ladder (below).

**Verified from the docs and the installed types (SDK 8.2.0, no Slack needed):**
- The id is read at `res.files[0].files[0].id` (`filesUploadV2` returns one `completeUploadExternal` answer per upload group, each with `files[]`); the block built is exactly `{type: "image", slack_file: {id}, alt_text}` (`imageBlock` in `src/slack/spikeProbe.ts`, tested): no `image_url`, no extra field, `id` a plain string. The json pointer `slack_file.id/slack_file` is Slack's way of naming the rejected `slack_file` object, not a sign of a wrong nesting.
- Slack's guide on private images in Block Kit (slack.com/blog/developers/uploading-private-images-blockkit): a file need not be shared to a channel, uploaded files are private to the uploader, and the posting identity must have access (use the same token for upload and post); PNG, JPEG and GIF only. It names no scope and no waiting time. The image-block reference page says nothing about access or errors.
- `files.info` needs `files:read`; the spike prints `missing_scope` as a finding if the app lacks it (the manifest has only `files:write`).
- The client may expose the granted scopes as `response_metadata.scopes` of `auth.test` (type exists in 8.2.0); the spike prints them or says they are not exposed.

**Hypotheses for the rejection, ranked (all unverified until the user runs `scripts/image-spike.ts`):**
1. **The file is not ready yet.** `completeUploadExternal` returns before Slack has finished processing the file; the post validates `slack_file` at once. Evidence for: the error is a validation of the file ("invalid slack file"), not `missing_scope`, `not_in_channel` or `file_not_found`; the helper returns right after completing; the docs are silent on timing. Test A (retries after 0.5, 1, 2, 4, 8 s) answers it and prints how long it took.
2. **A private file does not resolve in the DM of another conversation.** Docs: "the user posting must have access". The guide says sharing is not needed, but it does not cover a bot posting to a user's DM that was opened by `chat.postMessage` with a user id. Evidence against: the same bot token uploaded and posts. Test B (upload with `channel_id` = the DM) answers it.
3. **Slack did not recognise the upload as an image.** The Buffer is uploaded under the name `card-N.png`; if the stored `mimetype`/`filetype` is not `image/png`/`png` the block is invalid. `files.info` prints both; a mismatch is printed with `!!`. Tests B to D change how the file is uploaded.
4. **The `id` form is rejected but `url` works.** Both are allowed by the docs. Test C posts `slack_file: {url}` with the file's `url_private` (never printed).
5. **The token lacks a scope for resolving files (`files:read`)**. Less likely (a missing scope normally has its own error), but the printed scopes and the `files.info` result settle it.
6. **Our code sent a wrong id.** Unlikely: the id printed by the user has the `F…` shape and is the one the SDK returned.

**The ladder** (first card; the strategy that works is used for the other cards): A private upload, `files.info`, post with the 0.5/1/2/4/8 s retries; B upload with `channel_id` = the DM (puts a separate file message into the DM; the DM channel id comes from an intro text message, which is an extra message); C `slack_file.url`; D the explicit `getUploadURLExternal` + POST + `completeUploadExternal` route with `channel_id`. A full run in which nothing works takes about 70 seconds (four strategies, 15.5 s of retries each). The script also prints `auth.test` (the bot user id: the same token uploaded and posted), the scopes, the block JSON that was sent and, per card, the timings and the number of attempts.

**What the user pastes back:** the whole output of `npm run spike:image -- --email <you>`; which strategy printed `ACCEPTED` and after how many seconds; whether a separate file message appeared in the DM (B, D); whether the image shows in the card; and after the clicks whether the image stayed or went.
